# デジタルシール帳アプリ 仕様・実装計画

## 1. 概要

ユーザーが自分の写真から「デジタルシール」を生成し、アプリ内のシール帳に収集・閲覧し、対面で他ユーザーと交換できる iOS アプリケーション。

本アプリの中心的な価値は、シールを「作れること」ではなく **1枚ごとに固有であり、複製できないこと** にある。したがって設計上の最優先事項は、生成枚数の制限と、加工パラメータの乱数決定による個体差の担保である。

サーバーにコンテンツを保存せず、シールの実体と流通はすべて端末間（P2P）で完結する。

---

## 2. 中核コンセプト：唯一性の担保

唯一性は、以下の三層で成立させる。

### 2.1 生成機会の制限

シール化の権利は**6時間で1回復**する。無制限に生成できないことで、1枚あたりの重みを維持する。

### 2.2 加工パラメータの乱数固定

シール生成時、加工の見た目を決めるパラメータ群（キラキラの密度・パターン・色相・流動速度など）を乱数で決定し、シール個体に**恒久的に固定**する。

- 同じ写真から2枚作っても、光り方が異なる別個体となる
- パラメータは個体データに含まれるため、**交換して他人の端末に渡っても、同じ光り方で再生される**
- レンダリングは決定論的であり、パラメータが同一であれば常に同一の見た目になる

### 2.3 加工グレードの抽選

加工の質（レア度）は選択制ではなく**抽選制**とする。豪華な加工を任意に連発できないため、同一の被写体で高レア個体を量産して価値を下げることができない。

生成権とは別枠の消費リソースとして扱う。

## 3. 機能仕様

### 3.1 シール生成

**入力**

- カメラロールからの選択
- その場での撮影

**切り抜き（3方式）**

| 方式 | 内容 |
|---|---|
| 自動 | 被写体を自動検出し、輪郭に沿って切り抜く |
| 定型 | 円・角丸四角形などの既定形状で切り抜く |
| 手動 | ユーザーが指でなぞって形状を決定する |

**加工タイプ**

- フラットシール（平面・標準）
- ぷっくりシール（厚みと立体的なハイライトを持つ）
- 水入りシール（内部に流体と粒子を封入した表現。端末の傾きに追従して内容物が移動する）

**生成演出**

生成完了時、シールが回転しながら定位置に着地する演出を挟む。生成処理の待ち時間を演出として消費させる。

### 3.2 シール帳（ビューア）

シール帳は保管庫であると同時に、**眺めること自体が主要な体験**となるよう設計する。

- ジャイロセンサーに追従し、端末の傾きに応じて各シールの光沢・反射が変化する
- 見開き単位のページめくりに対応する
- 各シールの物理的な材質差（フラット／ぷっくり／水入り）が、傾けた際の挙動の違いとして知覚できること

### 3.3 個別拡大ビュー

シールをタップすると単体の拡大ビューに遷移する。カードゲームアプリにおけるカード鑑賞画面に相当する体験を想定する。

- 傾きに応じた光沢変化を最大解像度で表示
- 生成日・来歴（交換履歴）などのメタ情報を併記
- 拡大ビューへの遷移および表示中は、フローティング系のエフェクトを用いる

### 3.4 ウィジェット

生成したシールを**ロック画面およびホーム画面のウィジェット**として配置できる。

ウィジェットに使用中のシールは、シール帳上では**点線の外枠のみの表示**となり、実体がそこにないことを示す。1枚のシールは同時に1箇所にしか存在できないという原則を、視覚的に表現する要素として機能させる。

### 3.5 交換

- **対面のみ**に限定する。遠隔交換は提供しない
- 近距離無線通信（AirDrop 相当の端末間直接転送）で行う
- 譲渡したシールは自分のシール帳から消失する

対面限定とすることで、交換体験の希少性を保つと同時に、未知のユーザーとの接触機会を構造的に排除する。

### 3.6 複製の不可能性

- 生成済みシールの複製機能は提供しない
- 加工パラメータが乱数で固定されるため、同一個体を再生成することもできない

## 4. UI / ビジュアル方針

### 4.1 基本方針

BeReal および setlog を参照し、**機能を絞ったシンプルな構成**とする。設定項目・タブ数・操作段階を最小限に保つ。若年層を主要ターゲットとする。

### 4.2 グラフィック表現

ネイティブアプリでありながら、グラフィック効果を積極的に活用する。

- 最新 iOS の Liquid Glass 表現を全面的に採用し、シールの表示面でも活用する
- 生成時・拡大表示時・遷移時にフローティング系のエフェクトを多用する

シンプルなUI構造と、リッチな表現の両立が方針である。

## 5. 技術構成

| 領域 | 採用技術 |
|---|---|
| プラットフォーム | iOS のみ（ネイティブ実装） |
| UI | SwiftUI |
| 被写体自動抽出 | Vision（前景インスタンスマスク生成） |
| 加工レンダリング | Metal / SwiftUI Shader |
| 傾き検出 | Core Motion |
| ウィジェット | WidgetKit + App Group |
| 端末間転送 | Multipeer Connectivity ないし共有シート経由のファイル転送 |
| 署名・鍵管理 | CryptoKit（Ed25519）、Secure Enclave |
| 永続化 | SwiftData ないし Core Data（端末内） |

Android 版および Web 版は本計画の対象外とする。

## 6. データモデルと拡張性

### 6.1 設計原則

加工の種類と台紙デザインは、リリース後に継続して追加・更新される前提で設計する。したがって、これらを **enum やハードコードされた分岐として実装してはならない**。定義データとして外部化し、個体レコードはその定義を ID で参照する。

原則は以下の通り。

- 加工・台紙は **カタログ（定義データ）** と **インスタンス（個体）** に分離する
- 個体は定義を ID とバージョンで参照し、パラメータの実値を自身に保持する
- パラメータは固定フィールドではなく**キーと値の辞書**とし、新しい加工が新しいパラメータを持ち込めるようにする
- 未知の ID を受け取った場合も、アプリがクラッシュせず代替表示にフォールバックする

### 6.2 シール個体

```
StickerInstance
├─ id: UUID
├─ sourceImage: 端末内の画像実体への参照
├─ shape: 切り抜き形状データ（マスクまたはパス）
├─ effectID: String          例 "water.v2"
├─ effectVersion: Int
├─ grade: String             抽選で決定した加工グレードの識別子
├─ renderParams: [String: Float]   乱数固定された加工パラメータ群
├─ schemaVersion: Int
├─ createdAt
├─ transferChain: 署名付き譲渡履歴
└─ placement: inBook | inWidget
```

`renderParams` は生成時に一度だけ確定し、以後変更されない。この不変性が個体の同一性を定義する。辞書形式とすることで、将来追加される加工が独自のパラメータ名を持ち込んでも、個体レコードの構造を変更せずに済む。

### 6.3 加工カタログ

加工の定義は、アプリに同梱される宣言的なデータとして持つ。

```
EffectDefinition
├─ id: String                  一意かつ不変
├─ version: Int
├─ displayName
├─ shaderFunction: String      Metal 関数名
├─ paramSchema: [ParamSpec]    パラメータ名・範囲・乱数分布
├─ gradeWeights                グレードごとの出現重み
└─ fallbackEffectID: String?   未対応時の代替
```

パラメータの乱数決定は `paramSchema` を読んで汎用的に行う。加工を追加する作業は、**定義データ1件とシェーダー関数1つの追加**に閉じ、生成ロジック側の変更を伴わない状態を目標とする。

### 6.4 台紙カタログ

```
PageThemeDefinition
├─ id: String
├─ version: Int
├─ displayName
├─ background: 画像またはグラデーション定義
├─ slotLayout: シール配置スロットの座標・サイズ
├─ decorations: 装飾要素
└─ availability: 常設 | 期間限定 | 条件付き
```

シール帳のページは、台紙 ID と各スロットへのシール ID の対応のみを保持する。台紙を差し替えても、貼られているシールの同一性には影響しない。

### 6.5 バージョン差異への対応（重要）

サーバーを持たないため、**加工と台紙の定義はアプリ本体の更新でのみ配布される**。結果として、新しい加工で作られたシールが、それを知らない旧バージョンの端末に交換で渡る事態が必ず発生する。

以下の方針で対応する。

- 未知の `effectID` を受け取った場合、`fallbackEffectID` ないし汎用のフラット表示で描画する
- 個体データは欠損させず完全に保持する。アプリ更新後に本来の見た目で表示できること
- 当該シールには「アプリを更新すると本来の表示になる」旨を表示する
- 転送時にシェーダーコードそのものを送ることはしない（任意コード実行を招くため）。送るのは ID とパラメータのみ

### 6.6 譲渡

譲渡は `transferChain` への署名追加として表現する。中央サーバーを持たないため、二重譲渡の**防止**は行えず、履歴の分岐を**検出**して当該個体を無効表示する方式を採る。

譲渡は `transferChain` への署名追加として表現する。中央サーバーを持たないため、二重譲渡の**防止**は行えず、履歴の分岐を**検出**して当該個体を無効表示する方式を採る。

## 7. 技術的リスクと検証事項

| 項目 | 内容 |
|---|---|
| 加工表現の再現性 | 3種の材質が、傾けた際に明確に異なる質感として知覚されるか。本アプリの成否を左右する最大の要素であり、最優先で検証する |
| ウィジェットの表現制約 | ウィジェットはジャイロ追従や連続アニメーションを扱えない。静止画としてどう魅力を維持するか設計が必要 |
| 描画負荷 | 見開きページに多数のシールを同時表示し、全てを傾きに追従させた際のフレームレートおよび発熱 |
| バージョン差異 | 未知の加工で作られたシールが旧バージョン端末に渡る。フォールバック描画とデータ完全保持で対応する（6.5 参照） |
| 鍵の喪失 | 機種変更・端末紛失時にシール帳が全消失する。運営が復号できない形での iCloud バックアップを検討する |
| 権利処理 | 版権キャラクター等がシール化された場合の扱い。コンテンツを中央保持しない設計とあわせ、利用規約および法務確認が必要 |

## 8. 実装計画

### フェーズ0：加工エンジンの技術検証

シェーダーによる3材質の試作、ジャイロ追従の応答性検証、乱数パラメータによる個体差の目視確認。

**この段階で「眺めて楽しい」水準に到達しない場合、以降の計画を見直す。**

### フェーズ1：生成とシール帳

生成権のタイマー、3方式の切り抜き、加工の抽選と固定、シール帳のページめくりと閲覧、個別拡大ビュー。

この時点で単体アプリとして成立させる。交換機能がなくても、記録アプリとして使える状態を目標とする。

### フェーズ2：交換

鍵ペア生成、署名チェーン、対面での端末間転送、譲渡による消失、来歴表示、分岐検出。

### フェーズ3：ウィジェットと外部連携

ウィジェット配置、点線外枠表示、シール帳の画像書き出しと外部SNSへの共有。

### フェーズ4：クローズドベータ

実利用における生成頻度・交換頻度の観測、6時間という回復間隔および抽選確率の調整。

## 9. 対象外とする事項

**収益化は本計画の対象外とする。** アプリ内課金・広告・サブスクリプションのいずれも実装しない。サーバーを持たない構成のため運用費が発生せず、当面は収益設計を保留したまま開発を進められる。

生成権の追加購入等を設けないことで、希少性の設計が課金圧力によって歪む余地もない。将来的に検討する場合も、生成権そのものではなく台紙や加工のバリエーションを対象とする方が、既存の設計と整合しやすい。

- 年齢層に応じた利用上の配慮
